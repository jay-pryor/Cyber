## 1. Purpose

The design spec settled *what* the module and its contract are. The plan holds the
step-by-step tasks. This document is the third thing needed to finish: what is
actually built, what remains, in what order, and every decision and trap that
execution turned up. It exists so the work can be completed by a session — or a
person — that was not present for the first nine tasks.

## 4. Decisions taken during execution

These are settled. They amend the design spec where they contradict it.

| # | Decision | Why |
|---|---|---|
| D8 | **7d runs last on the critical path**, after 8/9/10 — not before 8. | Its gate is "the closure analysis returns `[]`", which cannot happen until `gather`, `gatherKept`, `relevanceFilter`, `relevanceKeyOf`, `ctxFor` and `deviceMeta` have left the moving code. Running it earlier means failing the gate or ignoring it, and ignoring it is the error 7a–7d was replanned to prevent. |
| D9 | **`buildReport` stays in CH.** The file is SPLIT, not moved. | It is the host's entry point and takes CH shapes (`project`, `deviceId`). Only `reportBlocks`, `sectionContent`, `sectionColumns` and `hostProvider` move. |
| D10 | The provider list travels as **`opts.providers`**, never `opts.sections`. | `opts.sections` is already the include-map of which sections are ticked. The collision is silent and produces `.filter is not a function` deep in rendering. |
| D11 | **`provider.rows` is optional.** Absent ⇒ the module passes `[]` and the provider sources its own data. | `buildControlSection` aggregates across every dataset, reading `displayKey` per adapter and satisfaction state off the store. A section spanning all datasets has no single row list the module could hand it. Amends design spec §4.2. |
| D12 | Providers are **bound per generation run**; their **columns are static**. | Each closes over the project/device/filter it describes, so the module never carries them. But the designer asks for columns with no run in hand, hence the unbound fallback in `sectionColumns`. |
| D13 | **`App.generate` is retained as a forwarding surface** after 7d. | CH has 192 suites and a Generate tab written against it. Churning them buys nothing and would obscure whether 7d changed behaviour. |
| D14 | **Remove a name from `BOUNDARY_DEBT` BEFORE the task that clears it**, not after. | The build then enumerates the exact call sites still to fix, instead of leaving you to hunt for them. This matters most in Task 9. |
| D15 | **The designer's CSS is extracted** as Task 14 (§5). | A module that ships an unstyled workspace is not reusable in any useful sense. |
| D16 | Tasks 11 and 13 stay in scope, off the critical path. | Both are quality work. Neither blocks the contract from functioning. |

## 5. Newly identified gap: the module has no stylesheet

`doc-designer.js` ships **JavaScript only**. `src/build-doc.json` names no style parts,
and the designer's rules live mixed into CH's stylesheets:

| File | Designer rules | Total rules |
|---|---|---|
| `src/style/010-part.css` | 0 | 120 |
| `src/style/020-vf-8-….css` | 48 | 223 |
| `src/style/030-a-hand-authored-….css` | 149 | 214 |

At least **197 of 558 rules are the designer's** (a floor — the count matches
line-initial `.rd-`, `.rpt-`, `.mdp-` and `.prev-` selectors only, so grouped and
nested selectors are missed).

A host adopting the module today gets a functioning but entirely unstyled workspace.
That is not a reusable module, and the design spec did not notice it because the
analysis that produced it looked only at JavaScript dependencies.

**Task 14** therefore: move the designer-owned rules into `src/doc/style/`, add a
style part to `src/build-doc.json` emitting `doc-designer.css` (or inlining the CSS
into the bundle, which suits an offline single-file host better), and leave CH's rules
in `src/style/`. The prefix convention makes the split largely mechanical; the risk is
shared base rules the designer silently depends on (typography, form controls,
`--tokens`), which will only show up by eye. Verification is therefore visual, not
automated: open `doc-designer.js` in a bare page and confirm the workspace is usable.

Sequence it **after Task 12**, so the split is done against a module whose boundary is
already settled.

## 6. Invariants and traps

Hard-won during execution. Each cost a debugging cycle.

- **A suite lives in the tree whose code it drives.** A test touching `App.store`,
  `App.registry`, `App.generate`, `App.ui.*` or `App.providers` is host code and
  belongs under `src/app/`. Getting this wrong fails the *build*, not the suite.
- **A fragment appended after a block that already closed its IIFE lands outside the
  closure.** It throws at load, before any suite registers, and the run used to report
  green over code that never executed. `tools/run-selftests.js` now exits non-zero on
  load errors. The build's closure check cannot catch this — the orphaned fragment is
  bracket-balanced, so depth analysis sees nothing wrong.
- **`--filter` needs the file path given explicitly:**
  `node tools/run-selftests.js ch-config-tool.html --filter GOLD-1`. The runner reads
  the first non-`--` argument as the file to load.
- **A generated file carries `.content`, not `.text`.** `buildReport(...)` returns
  `{name, files: [{name, content}]}`, where the outer `name` is the download filename.
- **`adapter.columns` is the Data tab's editable table**, not the report's columns
  (`reportColumns`). They are different sets of different things. An adapter is
  presented AS a provider by `providerFor()`; it is never renamed into one.
- **`App.util` is split across trees** — `base` owns `html`/`dom`/`stable`, `app` owns
  `clock`/`hash`/`zip`/`csv`/`crc32`/`idbKv`. The boundary check matches
  fully-qualified names, longest first, and ignores `App.x = App.x || {}` namespace
  guards.

## 7. Risks

| Risk | Mitigation |
|---|---|
| **Task 9's 43 edits fail quietly.** A missed call site keeps working until the wrong code path runs. | Apply D14: remove `store` from `BOUNDARY_DEBT` first, so the build lists every remaining site. Run Task 9 after Task 8, when the boundary check is doing more work. |
| **Task 8 rewrites `reportBlocks`,** which every generated document passes through. | GOLD-1 is the gate. It has caught nothing so far because nothing has changed output; the first time it fires, the step is wrong. |
| **Byte-neutrality may block a genuine improvement.** | It should. Any output change gets recorded as a defect and reviewed on its own, never absorbed into a refactor commit. |
| **Task 14's split is verified by eye.** | Accepted. Sequence it last, and treat a visibly broken workspace as the failing test. |

## 9. Effort

Roughly **one week** to the end of Task 12, then **three to four days** for Tasks 11,
13 and 14. Against the one week estimated at the outset for the whole extraction, the
honest total is about two and a half weeks.

The overrun sits entirely in Tasks 7–9 and has one cause: the original analysis
examined the module boundary carefully and never examined how `generate` was
internally wired, so every surprise came from CH's internals rather than from the
contract. The contract itself has taken no structural change — subject, filter,
providers, the host object and `getState`/`commit` are all as designed. The two
amendments (D10, D11) are details.
