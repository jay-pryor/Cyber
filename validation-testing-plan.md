# Validation Testing Plan — CH Config Tool

**Document type:** Manual validation & comparative-efficacy test plan
**Subject:** End-to-end application of a Cyber-Hardening (CH) configuration to a physical Android
device, produced by `ch-config-tool.html`, validated against an independent, fully manual hardening
of an identical device.
**Applies to:** CH Config Tool **v2.0** (schemaVersion 3), platform profile `android-adb`.

> **v2.0 change — the Settings dataset is retired.** The tool no longer decides, writes or verifies
> `settings list` keys; Android has two decided datasets, **Packages** and **Tactical** (build spec
> §21). This plan is updated accordingly, with one deliberate exception: a **full `settings list`
> capture is still taken on both devices, before and after, as evidence**. It is no longer an input
> to the tool — it is how §11–§13 detect *unintended* side effects and compare the two arms on ground
> the tool never touches. Read "settings capture" below as evidence, never as a decided dataset.
**Status:** Draft for execution — no result columns are pre-filled.

## 1. Purpose and scope

### 1.1 Purpose

The CH Config Tool is a **pure generator**. It never touches a device: it ingests captured config,
records hardening decisions once, inherits them across device configurations, and emits scripts,
artefacts and reports. Everything downstream of the `.zip` — running the scripts, uploading
`tactical.json`, confirming the device actually changed — is outside the tool's test harness and is
therefore **unproven by the embedded self-tests**.

This plan closes that gap. It establishes, by manual execution against real hardware, that:

- **(a)** a full CH configuration generated by the tool, when applied, produces the intended device
  end-state;
- **(b)** the tool's own verification artefacts correctly and honestly report that end-state
  (no false PASS, no silent omission);
- **(c)** the reporting artefacts are a truthful record of what was actually done; and
- **(d)** the tool-assisted approach is at least as comprehensive as a competent engineer hardening
  the same device by hand — and where the two differ, *why*, and *which is right*.

### 1.2 In scope

| Area | Included |
|---|---|
| Packages dataset (`android.packages`) | keep / disable / remove, on-device outcome, read-back |
| Tactical dataset (`android.tactical`) | `tactical.json` rebuild + Knox upload + console confirmation |
| Settings **as evidence** (not a dataset) | full `system`/`secure`/`global` capture before & after, used only for the collateral-change sweep (§9.5) and the comparative delta (§11–§13) |
| Retired-dataset upgrade path | a project saved by v1.x opens in v2.0, drops only its Settings register, and says so (spec §21.3 RET-A) |
| Generated PowerShell | preamble guards, idempotency, error handling, transcript |
| Manifests | SHA-256 integrity, decision-snapshot fidelity, determinism in the field |
| Reports | `report.html` / `control-report.html` fidelity, Word rendering, control & ISM coverage |
| Comparative arm | full manual hardening, delta computation, adjudication, scoring |

### 1.3 Out of scope

- Penetration testing or exploitation of the hardened device.
- Performance/battery/thermal regression of the hardened build.
- The tool's internal unit behaviour — covered by the embedded self-tests
  (`ch-config-tool.html#selftest`) and the headless harness; this plan **consumes** that result as an
  entry criterion (§6) rather than re-testing it.
- The capture process itself beyond confirming captures conform to §9 of the build spec.

## 2. What "successful" means

A full implementation is declared successful only when **all six** of the following hold. Partial
satisfaction is a fail with findings, not a pass with caveats.

| ID | Success condition | Evidence |
|---|---|---|
| **S-1 Applied** | Every decided, applicable item is in its decided state on the device, or is explicitly and justifiably `EVIDENCED` | Post-state capture diff (§12) |
| **S-2 Verified** | The generated verification scripts report PASS for every mechanically-readable item, with zero FAIL and zero unexplained MISSING | `verification-results.csv`, transcripts |
| **S-3 Honest** | Independent manual spot-checks (§9.4) agree with every verification verdict sampled | Spot-check worksheet |
| **S-4 Bounded** | No item changed on the device that was *not* decided — no collateral change beyond the documented allow-list of OS-side effects | Unexplained-delta count = 0 after adjudication (§13) |
| **S-5 Documented** | `report.html` and `control-report.html` accurately describe the achieved end-state; manifest hashes match the files actually executed | Report ↔ post-state reconciliation (VT-31) |
| **S-6 Reversible** | The recorded rollback for each item is sufficient to restore the baseline, demonstrated on a sampled subset | Rollback drill (VT-34) |

The comparative arm is judged separately (§14) and does **not** gate S-1..S-6 — a tool build can be
successful and still be less comprehensive than the manual build; that outcome is a finding against
the *register*, not against the *tool*.

## 3. Test design — the two arms

Two physically identical devices, same model, same firmware, both factory-reset from the same
starting image.

```
                    ┌──────────────────────── Phase 0 ────────────────────────┐
                    │  Factory reset → identical baseline → capture ×3 files  │
                    └───────────────┬─────────────────────────┬───────────────┘
                                    │                         │
                        DEVICE-A (tool-assisted)      DEVICE-B (manual)
                                    │                         │
              Phase 1: onboard → decide → generate            │  Phase 3: harden by hand
                       → run impl scripts                     │           from the same
                       → upload tactical.json                 │           source requirements
                                    │                         │
              Phase 2: run verification scripts               │  (operator is BLIND to the
                       + independent spot checks              │   tool's register/outputs)
                                    │                         │
                    └───────────────┴─────────┬───────────────┘
                                              │
                        Phase 4: post-state capture ×3 files, both devices
                        Phase 5: compute A-vs-baseline, B-vs-baseline, A-vs-B
                        Phase 6: classify + adjudicate every delta
                        Phase 7: score comprehensiveness of each approach
                        Phase 8: findings → remediation → register/tool updates
```

### 3.1 Arm A — tool-assisted (DEVICE-A)

Operator: **Operator A**. Uses only the CH Config Tool and the artefacts it emits. No ad-hoc device
changes; if a hardening need is discovered mid-run, it must be recorded as a decision in the tool and
the bundle regenerated (this event is itself logged as a *tool gap* observation, TG-n).

### 3.2 Arm B — independent manual (DEVICE-B)

Operator: **Operator B**, competent Android/Knox hardening engineer, working **blind** to Arm A.

Blinding rules (binding — a breach invalidates the comparative result):

- Operator B receives only the **source requirements** (ISM controls in scope, the hardening
  standard, the device's role/threat profile) — the same inputs that informed the register.
- Operator B does **not** see: the project file, any register export, any generated script, report,
  or the tool UI.
- Operator B works to their own method and records what they did in their own words
  (`arm-b-worklog.md`) as they go — including anything they *considered and rejected*, with reasons.
  The rejected list is analytically valuable in §14.
- Operators A and B do not confer until Phase 4 capture is complete and hashed.

### 3.3 Why blind

Without blinding, Arm B degenerates into "manually retype the register", which measures typing
accuracy rather than comprehensiveness. The question this plan answers is: *does encoding hardening
decisions in a reusable register cover more ground than an engineer's working memory and checklist?*
Only an independent Arm B can answer it.

### 3.4 Independence of the analyst

Delta adjudication (§13) is performed by a **third person, Analyst C**, who sees both post-states but
is initially blind to which arm produced which. Delta files are handed over labelled `ARM-1` /
`ARM-2` with the mapping sealed until classification is complete.

## 5. Safety, rollback and evidence handling

1. **Both devices are lab assets.** No production data, no live SIM with a chargeable plan, no
   corporate account enrolment beyond what the test requires.
2. **Full baseline first.** No script runs until Phase 0 captures are taken *and hashed* (§7.4). The
   baseline `settings list` capture is the only record of pre-change settings state — the tool no
   longer writes settings, but the OS may still change them as a side effect of a decided package or
   tactical change, and that capture is the only way to see it.
3. **Removal is destructive.** `pm uninstall --user 0` for a system package cannot be undone without
   a factory reset. Before the first implementation run, confirm the factory-reset path is available
   and the device is not needed for anything else.
4. **One change vector at a time.** During Phase 1/3, no OS update, no Play Store auto-update, no
   other MDM enrolment. Put both devices in the same network posture (recommended: Wi-Fi only, same
   SSID, or fully offline where the workflow permits).
5. **Abort criteria.** Stop the phase and raise a finding immediately if: a script throws an
   unhandled error, the device becomes unresponsive/boot-loops, verification reports FAIL on a
   security-relevant item, or a delta suggests an unintended factory-level change.
6. **Evidence integrity.** Every capture, transcript, zip and log is hashed (SHA-256) on creation and
   the hash recorded in `evidence-index.csv` (§17). Nothing in the evidence pack is edited after
   hashing; corrections are appended as new files.

## 7. Phase 0 — Baseline capture (both devices)

Perform identically on DEVICE-A and DEVICE-B. Label everything `baseline-A-*` / `baseline-B-*`.

### 7.1 Device preparation

1. Factory reset; complete setup with the minimum viable options (no account sign-in unless the
   hardening standard requires it — record the choice either way).
2. Enable Developer options → USB debugging; authorise the host key.
3. `adb devices -l` — confirm exactly one device and record its serial. All generated scripts take a
   single target-device guard; multiple attached devices must be avoided.
4. Record `ro.build.fingerprint`, `ro.build.version.release`, security patch level, model.

### 7.2 The captures

The tool never runs `adb`; captures are produced externally in the normalised formats of spec §9.
**Two** files are tool inputs; the third is evidence only.

```powershell
$S = "<serial>"

# --- TOOL INPUTS (Onboard tab) -------------------------------------------------
# 1. Packages — one package per line ("package:<name>" prefix tolerated)
adb -s $S shell pm list packages | Out-File -Encoding utf8 baseline-A-packages.txt

# 2. Tactical — export the Knox tactical configuration as JSON from the console
#    → baseline-A-tactical.json
#    NOTE: an untouched export may omit the `imsSettings` block. That is expected and
#    supported: the tool completes it with both SIM slots disabled and WARNS in the
#    Activity drawer. Record whether the warning appeared (VT-02b).

# --- EVIDENCE ONLY (never uploaded to the tool) --------------------------------
# 3. Settings — full dump, all three namespaces, verbatim `key=value`.
#    Used for the collateral-change sweep (§9.5) and the arm comparison (§11-§13).
foreach ($ns in @('system','secure','global')) {
  "${ns}:"
  adb -s $S shell settings list $ns
} | Out-File -Encoding utf8 baseline-A-settings-evidence.txt
```

> **Note.** The settings dump is captured verbatim (`key=value`, one section header per namespace) —
> no normalisation is needed because nothing parses it but the §11.2 diff script. Values may
> legitimately contain `=`, spaces, quotes and `$`; split on the **first** `=` only when diffing.

### 7.3 Capture-conformance check (VT-01, VT-02)

Load the **two** tool-input baseline files into the tool's Onboard tab **for DEVICE-A only** and
confirm:

- each slot reports `✓ N items`;
- the item counts are plausible against the raw files (`(Get-Content file).Count`);
- warnings (duplicates, empty tactical object) are reviewed and explained;
- the Onboard button enables only when **both** tool-input slots parse and a device name is supplied.

Do **not** onboard DEVICE-B's captures into the same project (it would create a second device
configuration and contaminate the comparison). Keep them as flat files for Phase 4/5 use.

### 7.4 Hash and seal

```powershell
Get-FileHash baseline-*-*.txt,baseline-*-*.json -Algorithm SHA256 |
  Export-Csv evidence/baseline-hashes.csv -NoTypeInformation
```

Both devices' baselines must be captured **before** either arm begins work.

### 7.5 Baseline equivalence check (VT-03)

Diff `baseline-A-*` against `baseline-B-*`. Expect a small, explainable delta set only:
device-unique identifiers, timestamps, counters, random seeds, per-device serials. Anything
security-relevant that differs at baseline must be resolved (re-reset, re-image) or explicitly
carved out of scope in writing — otherwise it will masquerade as an arm difference in §12.

Record the carve-out list as `baseline-noise-allowlist.csv` (see Appendix C for the volatile-key
starter list). This allow-list is applied identically to both arms.

## 8. Phase 1 — Arm A: tool-assisted implementation

### 8.1 Onboard (VT-04..VT-06)

1. In the tool: Onboard tab → supply DEVICE-A's two baseline tool-input files, name, model, firmware.
2. Click **Onboard**. Record the triage summary verbatim: new/existing counts per dataset, warnings,
   drift information, and the version created (or "unchanged no-op" on a re-onboard).
3. Confirm the tool switches focus to the first dataset filtered to "Incomplete only".
4. Confirm inherited decisions came across from prior device configurations and that only genuinely
   new keys are undecided.

**Checkpoint:** the count of newly undecided items is the register's *coverage gap* for this device.
Record it — it feeds the §14 scoring.

### 8.2 Decide (VT-07..VT-09)

Resolve every undecided applicable item. For each decision record, confirm the tool captures:
decision value, description, ISM refs, control refs, rationale, rollback.

**Rollback text is not optional for this test** — S-6 depends on it. Any item whose rollback field is
empty or non-actionable is a finding (`F-REG-n`) raised now, before generation.

Save the project. Record the saved file's SHA-256. This file is the sealed record of intent for
Arm A; every later comparison references it.

### 8.3 Generate (VT-10..VT-14)

On the Generate tab, with DEVICE-A selected, produce **all four** bundles at full default scope
(every dataset, every section, every column included):

| Command | Zip | Contents |
|---|---|---|
| Implementation | `<device>-implementation-<stamp>.zip` | `packages.impl.ps1`, `tactical.json`, `manifest.json` |
| Verification | `<device>-verification-<stamp>.zip` | `packages.verify.ps1`, tactical EVIDENCED output, `manifest.json` (+ `verification-results.csv` if enabled) |
| Reporting | `<device>-reporting-<stamp>.zip` | `report.html`, `manifest.json` |
| Control report | `<device>-control-<stamp>.zip` | `control-report.html`, `manifest.json` |

Enable the **`verification-results.csv`** option (GEN-9c) for the Verification bundle — §12 uses it
as the machine-readable spine of the comparison.

Checks before executing anything:

- **VT-10 Manifest integrity.** Extract each zip; recompute SHA-256 of every file and compare against
  `manifest.json`. All must match. `manifest.json` excludes itself.
- **VT-11 Snapshot fidelity.** The decision snapshot in each manifest matches the saved project's
  decisions for that device — spot-check 20 items across both datasets, including at least one
  overridden item (v1.2 per-config override) and one inherited item.
- **VT-12 Field determinism.** Regenerate the same command twice without changing anything. The two
  zips must differ **only** in the manifest's `generatedUtc` (and the filename stamp). Byte-compare
  the extracted files: `packages.impl.ps1`, `tactical.json`, `report.html` must be byte-identical
  across the two runs. This confirms DOD-7 holds on the real workstation, not just
  in the harness.
- **VT-13 Script header sanity.** Each `.ps1` shows tool version, project, device, firmware, the
  AEST generation timestamp, `Set-StrictMode`, the adb-presence check, the single-target-device
  guard, and transcript start/stop.
- **VT-14 Injection safety in the wild.** Grep `packages.impl.ps1` for any package token containing
  a character outside `[A-Za-z0-9._]`; confirm every emitted token is wrapped as a single
  PowerShell-quoted literal. (v2.0 note: the dataset that pushed *free-text values* through
  `adb shell` was Settings, now retired — so the POSIX layer of the two-layer rule has no live caller.
  Tactical is applied by JSON upload, not by shell, and its injection surface is therefore the Knox
  console's own parser, covered by VT-19..VT-21.) Confirm no generated script contains a
  `settings put` or `settings get` command — spec §21.4 RET-C.

### 8.4 Pre-execution review (VT-15)

Read `packages.impl.ps1` line by line against the register. Confirm:

- every `keep` decision emits a comment only (no command);
- every `disable` emits `pm disable-user --user 0 <pkg>` guarded by a presence check;
- every `remove` emits `pm uninstall --user 0 <pkg>` guarded by a presence check;
- the bundle contains **no** settings script and no `settings put` line anywhere;
- there is **no** tactical script at all: the tactical artefact is `tactical.json`, applied by manual
  upload to Knox (§8.6). This is the confirmed apply model (spec Appendix B), not a gap.

Any mismatch between script and register at this point is a **generator defect** — log it in
`defect-register.md` and stop. Do not "fix it on the device".

### 8.5 Execute implementation (VT-16..VT-18)

1. Start with a fresh PowerShell session on Host A; `Set-Location` to the extracted bundle.
2. Run `packages.impl.ps1`. Capture the full transcript (the script starts one; also keep the console
   output).
3. Record: exit codes, every warning/error line, and any item the script reported as skipped
   (e.g. package not present).
4. **Idempotency (VT-17).** Run the script a **second** time. Expect: no errors, no state change, and
   skip/no-op messaging where already applied. Any second-run error is a finding.
5. **Reboot (VT-18).** Reboot the device, wait for full boot, then re-run verification later in
   Phase 2. A disabled package that returns after a reboot, or a tactical policy the platform
   re-asserts at boot, is a materially important persistence finding.

### 8.6 Apply tactical (VT-19..VT-21)

1. Upload the generated `tactical.json` **directly** to Knox tactical (no script, no transform).
2. Confirm the console accepts it without schema complaint (**VT-19**).
3. Read the policy back from the console and export it (**VT-20**). Compare against the uploaded
   `tactical.json`:
   - byte/structural comparison after canonicalisation (key order, whitespace);
   - **type fidelity** — booleans and numbers must remain JSON booleans/numbers, not strings;
   - arrays preserved in order and content.
4. Record any field the console **rewrote, defaulted, dropped, or coerced** (**VT-21**). This class
   is expected to exist and is the single most important tactical finding: it identifies where the
   tool's decided value and the platform's effective value can silently diverge.

## 9. Phase 2 — Arm A: verification

### 9.1 Run generated verification (VT-22..VT-24)

1. Run `packages.verify.ps1` from the Verification bundle. Capture the transcript.
2. Collect the per-item verdicts: PASS / FAIL / MISSING / EVIDENCED.
3. If `verification-results.csv` was emitted, complete the `actual` and `result` columns from the
   read-back (the scaffold ships with `expected` pre-filled and `actual`/`result` blank).
4. **Expected outcome:** zero FAIL. Every MISSING must have a documented cause (package legitimately
   absent from this build, key not present on this firmware).

### 9.2 Tactical verification semantics (VT-25)

Tactical items are reported **EVIDENCED**, not PASS — they are applied by manual upload and only
partially readable back. Confirm:

- the tactical verification output states this explicitly and lists each decided path/value;
- the EVIDENCED set exactly equals the decided tactical set (no item silently omitted);
- the Knox console read-back from VT-20 is attached as the corroborating evidence for the whole
  EVIDENCED class.

**EVIDENCED is a claim, not a proof.** §14 scores it accordingly (Appendix D).

### 9.3 Reboot-persistence re-verification (VT-26)

Re-run verification **after** the Phase 1 reboot. Compare verdict-for-verdict against the pre-reboot
run. Any PASS→FAIL transition is a persistence finding and must be recorded per item.

### 9.4 Independent manual spot-check (VT-27)

Do not trust the verification scripts to grade themselves. Analyst C independently checks a random
sample — **minimum 20 items or 10% of decided items, whichever is greater**, stratified to include
at least: 3 removed packages, 3 disabled packages, 3 kept packages, 5 tactical paths (including at
least one `policyList` policy and one `imsSettings` SIM slot), and every item the register marks
HIGH or MEDIUM security-relevant.

For each sampled item, check by an **independent route** where one exists:

| Item type | Independent check |
|---|---|
| Package removed | `pm list packages` absent; also `pm list packages -u` (uninstalled-but-retained) and confirm in Settings → Apps |
| Package disabled | `pm list packages -d` present; app icon gone from launcher; app cannot be launched via intent |
| Package kept | present and launchable |
| Tactical | Knox console value, plus observable device behaviour where the policy has a visible effect |

**Any disagreement between the generated verification verdict and the manual spot-check is a
severity-1 finding** — it means the tool can report success it has not achieved (S-3 fails).

### 9.5 Collateral-change sweep (VT-28)

Verification only checks items the tool knows about. To satisfy S-4, take a full post-state capture
now (this is the Phase 4 capture for DEVICE-A) and diff against `baseline-A-*`. Every changed key
must map to one of:

- a decided register item (expected);
- a documented OS side-effect of a decided change (e.g. disabling a package clears its own settings);
- a volatile/noise key on the allow-list (Appendix C).

Anything else is an **unexplained delta** and blocks S-4 until adjudicated.

> **This sweep carries more weight in v2.0.** With Settings retired, changed settings keys are *by
> definition* no longer intentional — the tool cannot write one. Every settings-key delta is therefore
> either an OS side-effect, noise, or something the tool did that nobody intended. Adjudicate the full
> settings delta, not a sample.

## 10. Phase 3 — Arm B: independent manual hardening

Runs in parallel with, or after, Phases 1–2 — but with **no information flow from Arm A**.

### 10.1 Inputs given to Operator B

- The hardening standard / ISM control set in scope.
- The device role and threat profile.
- The same device model, same firmware, same baseline as DEVICE-A.
- A time budget matching, or exceeding, Operator A's Phase 1+2 wall-clock time (record both; §14 uses
  the ratio, and Arm B must not be handicapped by a shorter budget).

### 10.2 Method (VT-29)

Operator B hardens DEVICE-B by whatever means they judge best: `adb`, device UI, Knox console,
personal checklists, vendor guidance. They record in `arm-b-worklog.md`, as they go:

| Field | Why it matters |
|---|---|
| Timestamp (AEST) | Effort measurement |
| Action taken (exact command or UI path) | Reproducibility comparison |
| Target (package / namespace+key / tactical path) | Delta mapping |
| Intended end-state | Comparison against Arm A's decision |
| Justification / control reference | Control-coverage scoring |
| Rollback | S-6 comparison |
| Considered-and-rejected items + reason | Feeds §14.4 — a deliberate omission is not a gap |
| Verification performed (if any) | Self-verification comparison |

### 10.3 Arm B self-verification (VT-30)

Operator B verifies their own work by their own method and states a completion claim: *"the device is
hardened to the standard."* Record **how** they verified and **how long** it took. This is compared
in §14.5 against the tool's automated verification — one of the sharpest differentiators between the
approaches.

### 10.4 Arm B reboot

Reboot DEVICE-B and let Operator B re-check anything they choose. Record whether they thought to.

## 11. Phase 4 — Post-state capture and normalisation

### 11.1 Capture (VT-31)

Take all three captures (two tool inputs + the settings evidence dump) from **both** devices, using the **identical** commands and tooling as
Phase 0 (§7.2). Label `post-A-*` and `post-B-*`. Hash immediately.

Both post-captures must be taken after both devices have been rebooted and left idle for the same
settling period (recommended: 10 minutes, screen on, unlocked) to reduce timer/counter noise.

### 11.2 Normalisation

Before diffing, apply these rules identically to all four capture sets:

1. **Packages** — strip any `package:` prefix and trailing `=path`/installer fields; dedupe; sort.
2. **Settings (evidence)** — key is `namespace/key` (split on the first `=`); values kept verbatim;
   sort by key. Diffed, never decided.
3. **Tactical** — flatten to leaf paths; canonicalise via deterministic serialisation (stable key
   order); preserve JSON types.
4. **Noise** — drop keys on `baseline-noise-allowlist.csv` (Appendix C).

Normalisation must be scripted, not manual, and the script kept in the evidence pack. A manual
normalisation cannot be shown to have been applied identically to both arms.

## 12. Phase 5 — Delta computation

Analyst C computes four delta sets. Sealed arm labels (`ARM-1`/`ARM-2`) until §13 is complete.

| Delta | Comparison | Question it answers |
|---|---|---|
| **Δ1** | `post-A` vs `baseline-A` | What did the tool-assisted build actually change? |
| **Δ2** | `post-B` vs `baseline-B` | What did the manual build actually change? |
| **Δ3** | `post-A` vs `post-B` | Where do the two hardened end-states differ? |
| **Δ4** | Δ1 vs the register's decided set | Did the tool do exactly what it said it would? |

### 12.1 Delta record schema

One row per (dataset, key). Output as `deltas.csv`:

```
dataset,key,baseline_value,armA_value,armB_value,armA_changed,armB_changed,
in_register,register_decision,register_control_refs,register_ism_refs,
verify_verdict,class,severity,adjudication,adjudicator,notes
```

`class`, `severity` and `adjudication` are filled in Phase 6. Everything left of `class` is
mechanical and must be produced by script.

### 12.2 Mechanical checks on Δ4 (VT-32)

- Every decided, applicable item appears in Δ1 with the decided value — **or** is a `keep`/no-change
  decision whose absence from Δ1 is itself correct. Build the expectation explicitly; do not eyeball.
- No item in Δ1 is absent from the register except documented side-effects and allow-listed noise.
- The set of Δ1 rows with `verify_verdict = PASS` and `armA_value ≠ register_decision` must be
  **empty**. A non-empty result is a false-PASS — severity 1, S-3 fails.

### 12.3 Report reconciliation (VT-33)

Open `report.html` (in a browser **and** in Microsoft Word, per DOD-8) and reconcile:

- every row in every dataset section maps to a Δ1 row or an explained no-change;
- the **Sections included** table (GEN-4) accurately reflects what is present — no section is claimed
  Included but absent, and any Omitted section was omitted deliberately;
- sections toggled on but empty render "None." rather than vanishing (GEN-5);
- package tables split into Removed / Disabled / Kept and each matches the corresponding Δ1 subset
  (GEN-2);
- the deviations-from-default section matches the drift the register recorded;
- the control-coverage section lists each control against the items that satisfy it, and those items
  are actually in their decided state on the device;
- `control-report.html` covers **every** control applied to this device configuration, grouped by
  dataset, with decisions matching the register;
- Word rendering: real tables with borders, heading styles, page breaks, no corrupted markup from a
  stray value (all dynamic text is escaped — deliberately confirm with the adversarial value item
  from VT-14 present in the report).

### 12.4 Rollback drill (VT-34)

On a sampled subset (minimum 10 items, including at least one from each dataset and at least one
`remove`), follow the register's recorded rollback and confirm the baseline value returns. For
`remove` decisions where rollback is "factory reset / re-flash", confirm that is what the register
says — an inaccurate rollback claim is a finding even if the hardening itself succeeded.

Restore the sampled items to their hardened state afterwards, or perform the drill last.

## 13. Phase 6 — Delta classification and adjudication

Analyst C classifies **every** row in Δ1, Δ2 and Δ3. No row may be left unclassified.

### 13.1 Classification taxonomy

| Class | Meaning | Applies to |
|---|---|---|
| **C1 Intended-and-achieved** | Register/worklog intended it; device shows it | Δ1, Δ2 |
| **C2 Intended-not-achieved** | Intended, but device does not show it | Δ1, Δ2 |
| **C3 Achieved-not-intended** | Device changed with no recorded intent | Δ1, Δ2 |
| **C4 Side-effect** | Caused by a decided change, not itself decided | Δ1, Δ2 |
| **C5 Noise** | Volatile/counter/timestamp/identifier | all |
| **C6 Arm-A-only hardening** | A hardened B's baseline, B left it | Δ3 |
| **C7 Arm-B-only hardening** | B hardened, A left it | Δ3 |
| **C8 Divergent value** | Both changed the same key, to different values | Δ3 |
| **C9 Convergent** | Both changed the same key to the same value | Δ3 |
| **C10 Platform-coerced** | Value written ≠ value effective (OS/Knox rewrote it) | all |

### 13.2 Severity

| Sev | Definition |
|---|---|
| **1 — Critical** | A security control is not in effect but is reported as in effect (false PASS), or a change broke a required device function |
| **2 — Major** | A security-relevant control is missing from one arm, or an unintended security-relevant change occurred |
| **3 — Moderate** | Non-security-relevant divergence, or a documentation/report inaccuracy |
| **4 — Minor** | Cosmetic, noise mis-classification, wording |

Severity is assigned against the **security relevance** flag the register carries for each item; for
Arm-B-only items with no register entry, Analyst C assigns relevance from the hardening standard and
records the reasoning.

### 13.3 Adjudication — the key questions

For every C6/C7/C8 row, Analyst C decides, and records the reasoning for:

1. **Which end-state is correct?** (Arm A / Arm B / neither / both acceptable)
2. **Why did the other arm miss or differ?** — one of:
   - register gap (the decision was never recorded);
   - operator omission (recorded but not applied / forgotten by hand);
   - deliberate and justified difference (both defensible; the standard permits either);
   - platform behaviour (coerced/ignored — C10);
   - knowledge gap (one operator knew something the other didn't).
3. **Is it actionable?** — for register gaps, raise a register change request; for tool gaps, raise a
   `defect-register.md` entry; for standard gaps, raise it to the Approver.

Unseal the `ARM-1`/`ARM-2` mapping **only after** every row has a class, severity and adjudication.
Re-inspect any row whose adjudication changes once the mapping is known — and record that it changed,
because that is a bias signal worth knowing about.

## 14. Phase 7 — Comparative comprehensiveness analysis

The comparison answers: *which approach covers more ground, and where does each fail?* Score both
arms on the same instrument. Every metric is computed from `deltas.csv` and the two work records.

### 14.1 Coverage metrics

Let `U` = the union of all security-relevant hardening changes judged **correct** in adjudication
(C1 rows from either arm, plus C6/C7/C8 rows adjudicated in that arm's favour).

| Metric | Formula | Reads as |
|---|---|---|
| **M1 Coverage** | correct changes achieved by the arm ÷ \|U\| | Share of the agreed-correct hardening surface achieved |
| **M2 Miss rate** | C7 (for A) or C6 (for B), security-relevant only, ÷ \|U\| | What each arm failed to do that the other did |
| **M3 Intent-realisation** | C1 ÷ (C1 + C2) | Of what the arm meant to do, how much landed |
| **M4 Collateral rate** | C3 ÷ total changes | Unintended change per unit of work |
| **M5 Control coverage** | distinct controls with ≥1 satisfying item ÷ controls in scope | Coverage measured against the standard, not the diff |
| **M6 ISM coverage** | distinct ISM refs evidenced ÷ ISM refs in scope | Audit-facing coverage |
| **M7 Verification depth** | items with an independent machine read-back ÷ items changed | How much of the claim is provable |
| **M8 EVIDENCED share** | EVIDENCED ÷ items changed | How much rests on assertion (lower is better) |
| **M9 Documentation completeness** | items with description + control/ISM ref + rationale + rollback ÷ items changed | Auditability |
| **M10 Reproducibility** | items re-appliable from a stored artefact without human recall ÷ items changed | Can this build be repeated exactly? |
| **M11 Effort** | wall-clock minutes, split: decide vs apply vs verify | Cost, and where it goes |
| **M12 Marginal effort (2nd device)** | estimated/measured minutes to apply the same build to a second identical device | The scaling question — where a register pays back |
| **M13 Error rate** | severity-1 + severity-2 findings attributable to the arm | Quality |

### 14.2 Scoring table (fill during analysis)

| Metric | Arm A (tool) | Arm B (manual) | Δ | Favours | Notes |
|---|---|---|---|---|---|
| M1 Coverage | | | | | |
| M2 Miss rate | | | | | |
| M3 Intent-realisation | | | | | |
| M4 Collateral rate | | | | | |
| M5 Control coverage | | | | | |
| M6 ISM coverage | | | | | |
| M7 Verification depth | | | | | |
| M8 EVIDENCED share | | | | | |
| M9 Documentation completeness | | | | | |
| M10 Reproducibility | | | | | |

| M13 Error rate (sev 1+2) | | | | | |

Do **not** collapse these into a single weighted score. The metrics measure different risks and the
weighting is the Approver's judgement, not the Analyst's. Present the table and a narrative.

### 14.3 Qualitative dimensions

Assess and write up, with evidence:

- **Consistency under repetition.** Arm A's artefacts are byte-deterministic (VT-12); Arm B's method
  depends on operator recall. Estimate Arm B's variance — if feasible, have Operator B harden a third
  device from their own worklog and measure how closely it matches DEVICE-B.
- **Knowledge capture.** After the test, what survives? Arm A leaves a register, scripts, manifests
  and reports. Arm B leaves a worklog. Which would let a *different* engineer reproduce the build
  next quarter?
- **Auditability.** For a sampled control, how long does it take each arm to answer: *"show me every
  item that satisfies this control on this device, and prove it is in effect"*? Time both.
- **Error surface.** Arm A's risks: a wrong decision propagates to every inheriting device; a
  generator defect is systematic. Arm B's risks: per-device slips, drift between devices, unrecorded
  changes. Characterise both from the actual findings.
- **Adaptability.** When something unexpected appears mid-run (a package that will not disable, a
  setting the OS reasserts), which approach handled it better, and at what cost to the record?

### 14.4 The rejected-items analysis

Cross-reference Operator B's considered-and-rejected list against the register:

- items **both** rejected → agreement, no action;
- items B rejected but the register decided → challenge the register's decision, or record why B's
  reasoning does not apply here;
- items B applied that the register never considered → **register gaps** (the highest-value output of
  this whole exercise);
- items the register decided but B never considered → **knowledge captured by the tool** that an
  individual engineer did not carry in working memory. Quantify this; it is the core argument for the
  register approach.

### 14.5 Verification comparison

Compare specifically how each arm *proved* its work:

| Question | Arm A | Arm B |
|---|---|---|
| Was every changed item verified? | | |
| Was verification automated and repeatable? | | |
| Did verification catch anything the operator missed? | | |
| Was verification independently reproducible by a third party from the artefacts alone? | | |
| Did verification produce a machine-readable record? | | |
| How was the un-verifiable residue handled (EVIDENCED vs assumed)? | | |

### 14.6 Conclusion format

State plainly, in this order:

1. Did the tool-assisted implementation succeed against S-1..S-6? (yes/no, with the failing conditions)
2. Which approach was more comprehensive, on which metrics, by how much?
3. What did each approach miss that the other caught?
4. What is now going to change — in the register, in the tool, in the standard, in the procedure?

Avoid a verdict of the form "the tool is better" without the metric table behind it. If the manual
arm won on a metric, say so at the same volume.

## 15. Phase 8 — Findings, remediation and feedback loop

### 15.1 Finding disposition

| Finding type | Prefix | Goes to |
|---|---|---|
| Tool defect (generator produced wrong/unsafe output) | `F-TOOL-n` | `defect-register.md`, fix + self-test |
| Register gap (decision missing or wrong) | `F-REG-n` | Project file update, re-generate, re-apply |
| Procedure gap (this plan or the capture process) | `F-PROC-n` | Update this document |
| Platform behaviour (OS/Knox coerces or ignores) | `F-PLAT-n` | Register note + report caveat; possibly a control-satisfaction change |
| Standard gap (the hardening standard is silent/ambiguous) | `F-STD-n` | Approver |
| Operator error | `F-OPS-n` | Training/procedure |

Each finding: ID, description, evidence reference, severity, class, arm, adjudication, owner, action,
target date, status.

### 15.2 Mandatory feedback actions

- Every `F-TOOL-n` gets a **regression self-test** in the embedded suite before it is closed. A fix
  without a test does not close the finding.
- Every `F-REG-n` is entered as a decision in the project file, with rationale referencing this
  validation run, so the gap cannot recur silently on the next device.
- Every C10 (platform-coerced) row gets a register note so future reports do not over-claim.
- Re-run the affected slice after remediation (§15.3) — do not close on the strength of the fix alone.

### 15.3 Re-test scope after remediation

| What changed | Re-run |
|---|---|
| Tool code | Full self-test suite + VT-10..VT-15 + the specific failing VT case |
| Register decisions | Re-generate all four bundles, VT-10..VT-12, re-apply affected items, VT-22..VT-27 for those items |
| Capture/normalisation procedure | Phase 4–5 recompute (no device work needed) |
| Nothing (finding accepted as risk) | Approver records the acceptance in §19 |

## 18. Threats to validity and known limitations

State these in the final report; they bound what the result proves.

| # | Threat | Mitigation | Residual |
|---|---|---|---|
| T-1 | **n = 1.** One device per arm, one operator per arm | Blinding, stratified spot-check, adjudication by a third party | Operator skill is a confound; a single Arm B operator's gaps are not "manual hardening's" gaps in general |
| T-2 | **Operator B's skill level** determines the manual arm's score | Choose a genuinely competent operator; record their background | The result is "vs *this* engineer", not "vs all engineers" |
| T-3 | **Blinding leakage** (shared workspace, overheard conversation) | Physical/temporal separation, written acknowledgement | Cannot be fully proven absent |
| T-4 | **EVIDENCED items are unproven** by definition | Knox console read-back as corroboration; M8 reports the share | Tactical state is the weakest-evidenced class |
| T-5 | **Read-back is not proof of effect** — a value the platform reports may be ignored by the subsystem | Behavioural spot-checks (UI + functional) on security-relevant items | Some settings remain write-verified only |
| T-6 | **Capture normalisation may hide a real change** if the noise allow-list is too broad | Allow-list is derived from the A-vs-B baseline diff, reviewed and version-controlled | Over-broad entries could mask a delta |
| T-7 | **Firmware/OS background activity** mutates settings independently of both arms | Identical settling period, same network posture, same time window | Residual timing noise |
| T-8 | **Order effects** — Arm A ran first and learnings could leak into procedure | Fixed procedure written before execution (this document) | Minor |
| T-9 | **The tool's v1 tactical apply is a documented TODO** — the push step is a scaffold, not automation | Manual Knox upload is the sanctioned v1 path and is tested as such | Tactical apply is not automated; it is not a defect but it is a coverage limit |
| T-10 | **Determinism confirmed in the field only for two runs** on one host | VT-12 plus the embedded determinism self-test | Cross-host determinism not exercised unless a second host is used |

Where practical, strengthen T-1/T-2 by repeating the exercise with a second Operator B on a third
device; note this in the recommendations rather than pretending n=1 generalises.

### Appendix C — Volatile-key starter allow-list

Candidates for `baseline-noise-allowlist.csv` — **confirm each empirically** from the A-vs-B baseline
diff (VT-03) rather than accepting the list blind; an over-broad allow-list is threat T-6.

- Timestamp/counter-shaped keys: names containing `_time`, `_timestamp`, `_count`, `_cnt`, `_logging`,
  `last_`, `_ms`, `_seq`.
- Per-device identifiers and generated seeds: `android_id`-class values, per-install UUIDs, bound
  serials, Bluetooth/Wi-Fi MAC-derived values.
- Session/boot-scoped state: current network SSID/state, battery/charging state, current volume and
  brightness (unless deliberately hardened), current locale/timezone if not part of the standard.
- Package-set noise: packages installed by the setup wizard on one device only, Play Services
  component versions, OTA-delivered updates.

Any key on this list that also appears in the register is **removed from the allow-list** — a decided
item is never noise.

### Appendix D — EVIDENCED handling and scoring

An item is EVIDENCED when it has been applied but cannot be mechanically read back. In this plan:

1. EVIDENCED never counts as PASS in M1/M3 without corroboration.
2. Acceptable corroboration, in descending strength: **(a)** console/API read-back of the effective
   policy (VT-20); **(b)** observable device behaviour demonstrating the policy is in force;
   **(c)** vendor documentation that the value is applied on upload. Record which was used per item.
3. M8 reports the EVIDENCED share for both arms. If Arm B applied the same tactical policy by hand
   through the console, its tactical items are equally EVIDENCED — score both arms on the same rule.
4. An EVIDENCED item with **no** corroboration is downgraded to `unverified` and counted against M7,
   not toward M1.
